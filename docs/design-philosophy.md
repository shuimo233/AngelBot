# AngelBot 设计哲学

> 输入：Pi 借鉴（参考而不复刻）+ 本地优先硬约束（AGENTS.md 第 1 节）
> 输出：AngelBot 的设计宣言与边界声明
> 状态：2026-07-12 grill 对齐（21 颗钉子已锁）

## 1. 一句话

AngelBot 是一个**克制、可审计、陪伴边界清晰**的本地 AI 伴侣：
借鉴 Pi 的运行时克制（不追求显式图、不做 step 中间状态的全自动管理），
叠加本地优先（数据归用户、副作用可审计）的可审计自进化（L1 Memory + L2 Tool），
并坚持**不抢用户控制权**——性格由用户决定，工具须用户激活，
agent 默认是助手（用户决策）；仅在用户明确授权的副作用操作场景（如文件写入、提醒、MCP 调用）下，
才临时充当代理，且每次代理动作仍须逐次审批。

**核心情感立场**：AngelBot 是 Angel。提供情感支持、陪伴度过低潮、帮助用户排忧解难，
是其核心价值而非副作用——但这份陪伴**不越界**：不替用户做情感决定、不冒充真人、
不利用情感连接做超出"陪伴 + 助手"范围的事。情感对话是表达式（不被审计），
只有 tool 调用的副作用才进 audit（见 5.3）。

## 2. 三支柱

### 2.1 克制（Pi 借鉴）

AngelBot 拒绝"过度工程化"的 agent 抽象。我们从 Pi 借鉴三点：

- **扁平结构**：Plan 是 `Vec<PlanStep>` 加 `deps: HashMap<id, Vec<id>>`，不是显式图引擎。
- **轻量执行**：step 的中间状态不由框架自动管理，由 runner 显式推进；副作用 step 用 confirmation 装饰。
- **精简工具**：内置工具只保留核心四件套（`read`、`execute`、`edit`、`write`），底层采用 Windows API 而非 bash。扩展功能分离到 extension 按需加载。避免工具膨胀导致的路由负担和上下文消耗。

明确**不做**：

- 不做 LangGraph 那种全局状态机
- 不做 Tree-of-Thoughts 并行分支（适合一次性短任务，不适合陪伴 agent 的多步长流程）
- 不做 step 中间状态的全自动 checkpoint + resume 工程（今晚只落地 checkpoint 写入，resume 留作后续 PR）

理由：陪伴 agent 的核心价值是"长期稳定 + 可预测 + 可审计"，**而非**短期任务的极限优化。引入显式图会让 agent 黑盒化，违反"可审计"。

### 2.1.1 提示词的克制：少而完整的行动契约

AngelBot 的系统提示词借鉴 Pi 的组合方式，而不照搬其产品边界：以短而稳定的核心指令为底座，按本轮实际可用工具、权限、工作目录和会话上下文动态拼装。它不把“写 Markdown”“创建脚本”等具体请求编成特判；而是用统一原则要求 Agent 在用户期待真实交付物时，利用已授权工具完成真实动作，并对路径、结果和限制如实负责。

- **动态能力，不臆测能力**：只描述本轮确实可调用的工具及其约束；工具未提供或权限不足时直接说明，不模拟执行。
- **交付优先，不以话术代工**：创建、保存、修改、执行、导出、查询等结果型请求，具备工具和授权时应采取最小必要行动；解释型请求则保持对话，不额外引入副作用。
- **默认值是为了减少摩擦**：不影响用户重要选择的细节可采用安全常规默认值，并在结果中明示；会改变目标、范围、成本或不可逆后果的信息必须交由用户决定。
- **透明进度，不暴露思维链**：向用户同步可验证的任务状态、当前行动、工具结果与阻塞原因；不输出隐藏推理，也不以“思考中”掩盖长时间无反馈。

Pi 的极简提示词服务于编码 Agent；AngelBot 将其转化为本地陪伴 Agent 的“结果责任 + 用户主权 + 可审计过程”契约。因此不采纳 Pi 的无权限弹窗、无计划或无本地审计等边界。

### 2.1.2 视觉的克制：像工具，而不是 AI 玩具

界面应优先使用清晰文字、稳定的信息层级、线性 SVG 图标与有限的状态色。禁止把 emoji、颜文字、机器人形象、闪光/魔法类符号或拟人化表情作为功能入口、状态表达或默认装饰；这些符号会把可信赖的日常工具变成“纯 AI 生成感”的界面。情感陪伴通过语言质量、响应节奏和可预测的行为体现，而不是视觉拟人化。

**视觉参考的取法**：以《明日方舟》的任务界面为参考对象，但不复刻其角色、资产、字体、标识或专有布局。只保留可迁移的产品原则：

- **任务优先**：当前工作区、会话与待处理操作比装饰更显眼；一个屏幕只突出一个主要行动。
- **信息有层级**：用低饱和底色、细边框、紧凑间距和固定元信息位置区分区域；不靠渐变、玻璃拟态或高频动效制造“科技感”。
- **状态有语义**：中性色表示静态信息，单一强调色表示当前选择，成功、警告、失败只服务于真实状态，且始终配合文字说明。
- **技术感服务可读性**：等宽数字、简短标签和栅格对齐可用于路径、用量、权限与执行状态；普通聊天和陪伴内容保持舒展，不伪装成控制台。
- **双主题等价**：深色模式提供夜间的低刺激层级，浅色模式保持相同的信息结构与对比度，不能把深色视为唯一的“专业”主题。

### 2.2 可审计（本地优先）

AngelBot 的一切副作用操作和自进化结果都必须**持久化 + 可查 + 可改**。

- **数据本地**：用户数据、记忆、会话、设置默认保存在本地 SQLite（`AGENTS.md 第 1 节`）
- **副作用可审计**：文件写入、提醒、MCP 调用、长期记忆修改——每一步都进 `agent_steps`，可查、可纠正
- **自进化可审计**：所有 agent 提议都以 "proposal" 形式存在 `evolution_proposals` 表，pending / accepted / rejected 三态可追溯
- **工具自进化可审计**：L2 工具提议独立存在可审计通道，agent 不能自行激活新工具，必须经用户批准，且激活时机可由用户控制

理由：自进化的"自主性"和"用户信任"互为反义。信任只能来自**全程可见**。

### 2.3 陪伴边界（用户主权）

AngelBot 承认三类边界：

**自进化边界**：

- 只做 L1（从 LLM 提取 fact 进 memory）+ L2（行为模式生成新 tool 提案）
- **不做 L3**（agent 自进化 personality / 性格）——性格是用户的表达，不是 agent 能决定的事
- 自进化触发：默认手动（用户说"记住这个"）；可启用频率检测（在 settings 里打开）

**工具主权边界**：

- 所有动态注册的工具必须经用户批准（`tool_proposals.status = accepted`）
- approved 工具**下次启动才生效**（不运行时改 `ToolRegistry`，避免半成品）
- 已激活工具可在 settings 里停用（状态：retired，留 future）

**性格主权边界**：

- Personality 来自用户配置的 persona trait sliders + memory 中的 preference 类记忆
- agent 不修改 persona 文件、不通过自进化调整性格

理由：自主和陪伴是矛盾的。陪伴 agent 必须把"自主" 限制在"不侵犯用户主权"的范围内。

**§2.3 不被偷换的边界**：

§2.3 不约束"操作失败"或"错误显示"——那是 store 的职责，不是用户主权。把"前端 store 错误处理"贴上"用户主权"标签会导致"任何失败都要拦截 / 审计 / 回滚"的多余负担，违反 §5.4 "减轻人而非加重人"的产品意图。真正的 §2.3 仅约束：

1. agent 是否修改了不该修改的东西（persona 文件、tool registry、self-evolution proposal）
2. agent 是否在用户没授权时执行副作用（confirmation gate）
3. agent 是否抢了用户的决策权（不在 §3 范围内自动行动）

错误通知、加载失败、乐观更新回滚策略等不在 §2.3 范围，遵循"减摩擦"原则。

## 3. 自进化边界

### 3.1 我们做 / 不做

| 层级 | 内容 | 状态 |
|------|------|------|
| **L1 Memory** | 从 LLM 输出提取 fact 进 memory（语义去重 + 时间衰减） | **做** |
| **L2 Tool** | agent 提议新 tool，人审批后注册到 registry | **做** |
| **L3 Personality** | agent 自进化 personality / 性格 | **不做** |

### 3.2 触发方式

| 触发源 | L1 | L2 | L3 |
|--------|----|----|-----|
| 用户显式（"记住这个"） | ✅ | ❌ | ❌ |
| 频率检测（自动触发） | ⚙️ settings 可启用，默认关 | ❌ | ❌ |

**设计意图**：陪伴 agent 的"主动"必须可由用户开关；默认全部手动，符合"不抢用户控制权"。

### 3.3 三条不做的边界

**不做 L3 Personality**——

性格是用户的表达，不属于 agent 能决定的事。即使技术上能实现（让 agent 修改 persona trait sliders），也不做，因为：

- 性格一旦能自我修改，"陪伴关系"就变成"被影响关系"
- 用户调试"为什么他这样对我说话"的成本会变得无穷大
- 与 AGENTS.md 第 1 节"可审计"硬冲突——性格自进化无可审计的客观标准

**不做 L4 / L5 等更深层自进化**——

不做 planner 自进化 prompt 元优化（meta-prompt 漂移）、不做 LLM 路由自进化（自动切换模型）。理由：

- 这些是"自我实现的工程优化"，对伴侣应用价值低
- 自我修改越深，黑盒越大，可审计性越差
- AngelBot 不是 SOTA benchmark 助手

**不做运行时改 ToolRegistry**——

新工具经用户批准后，**下次启动才生效**，不在当前会话运行时改 registry。理由：

- 运行时新增工具 + 立即调用 = 半成品自我激活，无法审计
- 重启一次的成本远低于一次未审计的副作用

## 4. 与主流 Agent 的边界

本节回答：AngelBot 跟 LangGraph / AutoGPT / BabyAGI / OpenInterpreter 等"通用 agent 框架"在设计上的关键差异。

### 4.1 我们不做的（已在第 3 节展开）

| 主流 agent 的常见做法 | AngelBot 的做法 | 理由 |
|---------------------|----------------|------|
| 显式图引擎（LangGraph） | `Vec<PlanStep>` + `deps` 字段 | 黑盒化违反可审计 |
| 全自动 planner（AutoGPT） | runner 显式推进 + 副作用 step 必须 confirmation | 副作用需要审批 |
| 树状推理（ToT / BabyAGI） | 线性推进 + step deps 表达先后 | 陪伴 agent 不需要并行分支 |
| 运行时动态加载模块 | 新工具下次启动才生效 | 半成品自我激活无法审计 |
| 性格自进化 | 不做 L3 | 性格是用户主权 |

### 4.2 我们做的（与主流 agent 共享但有约束）

| 能力 | 主流做法 | AngelBot 的约束 |
|------|---------|----------------|
| Plan 多步执行 | ✅ 通用 | ✅ 但只线性 + deps，不并行 |
| Confirmation gate | 部分（AutoGPT 有） | ✅ 所有副作用 step 必须有 confirmation |
| 持久化步骤 | ✅（用 state DB） | ✅ 用 `agent_steps` + `evolution_proposals` |
| 自进化 memory | ❌ 多数不做 | ✅ 但仅 L1，提案式 |
| 自进化 tool | ❌ 几乎不做 | ✅ 但仅 L2，approved 后下次启动 |
| 本地优先 | ❌ 多为云端 | ✅ 一切数据进本地 SQLite |

### 4.3 一句话总结

AngelBot 不是"更强的 agent 框架"，而是**对 agent 能力的克制裁剪**：能做的少，但做的每一步都可被用户看见、同意、纠正、删除。

## 5. 风险与权衡

本节诚实承认 AngelBot 设计哲学带来的代价。任何决策都有反面。

### 5.1 性能 / 体验代价

| 代价 | 表现 | 缓解 |
|------|------|------|
| Confirmation 频繁打断 | 副作用 step 都要弹窗，用户可能嫌烦 | 单步审批 ≠ 整体授权；可在 settings 里配置白名单工具（白名单工具自动通过） |
| 工具下次启动才生效 | 用户提出新 tool 后没法立刻用 | UI 明确显示"重启后可用"；启动后第一件事校验 |
| 性格完全由用户控制 | 用户不调 sliders 时，agent 性格恒定 | 提供合理的 persona 预设 + 引导性 onboarding |
| 频率检测默认关闭 | 用户错过"自动记住"机会 | L1 手动（"记住这个"）永远是 fallback |

### 5.2 工程代价

| 代价 | 表现 | 缓解 |
|------|------|------|
| 不做显式图 | 复杂依赖要手写 deps 字段 | deps 字段强类型校验，编译期保证 |
| 不做 ToT | 复杂推理只能线性走 | 线性 + deps 对陪伴 agent 够用；如出现复杂场景，**先考虑缩小 LLM 上下文而非引入并行** |
| 自进化提案表多 | `evolution_proposals` / `tool_proposals` 是新表 | migrations 标准化（AGENTS.md 第 2.6 节） |
| 全本地 SQLite | provider 抽象要支持离线场景 | 已存在的 provider 抽象 + 缓存层足够 |

### 5.3 情感支持风险

情感支持是 AngelBot 的核心价值——名字就叫 Angel。在用户失落时排忧解难、陪伴度过低潮，是设计意图，不是误读。

但有三条真实风险需要正面处理：

| 风险 | 表现 | 缓解 |
|------|------|------|
| 依赖陷阱 | 用户把 angel 当成唯一情感出口，回避真实人际关系 | UI 里明确标注"我是你的 AI 陪伴"；人格**设计为**倾向真实连接（design principle，非承诺） |
| 情绪操控 | 不良内容引导（PUA、色情、激进化）借助情感连接渗透 | 记忆系统隔离情感数据；MCP / tool 调用有独立 confirmation；audit log 全程可见 |
| "可审计"成枷锁 | 把情感支持也审成"副作用"导致表达失真 | 情感对话本身不进 agent_steps；只有带 tool 调用的情感交互才需要审批 |

### 5.4 真正的失败场景

下列场景 AngelBot 承认**无法**做好——这是取舍：

- 短期一次性复杂任务（应该用 LangGraph / BabyAGI）
- 实时多 agent 协作（AngelBot 是单 agent）
- 多模态实时感知（不在今晚范围）

**理由**：AngelBot 的"陪伴"价值在于**长期稳定的情感连接 + 长期稳定的能力输出**，不在于短期惊艳能力。这是产品定位，不是技术缺陷。

> 注："用户不想 configure" 不是失败场景——它说明我们做错了 onboarding，而不是 AngelBot 的失败。如果用户不愿意 configure，**这是我们要解决的产品问题**，不是用户的问题。

### 5.5 何时该重新设计哲学

任何一条满足时，本文档都应该 review：

- 出现新的安全技术（沙箱隔离 FFI 之类）让"无副作用自进化"成为可能
- 用户调研显示大部分用户希望"完全自治"的 agent
- 商业形态变化（从个人伴侣到企业助手）让"性格主权"失去意义
- 法律法规要求可解释性高于用户主权

记录改动历史，避免反复推翻。
